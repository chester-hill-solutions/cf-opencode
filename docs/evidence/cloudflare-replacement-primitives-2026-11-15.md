## Present portable capabilities

**Native workspace identity/readiness.** Aboiteau already prepares a genuine `/workspace`, persists `workspace_id`, root, working directory, registry and bucket separately under its state root, and validates restored `.stow` metadata. Fresh initialization refuses nonempty roots. `workspace serve --ready-fd` supplies fresh loopback endpoint/SigV4 credentials; readiness must match durable identity before OpenCode receives them. These paths and process contracts require Linux/Bun/tools, not Cloudflare. [Local validator](/Users/ladmin/WebProjects/cf-opencode/stow-workspace.ts), [control lifecycle](/Users/ladmin/WebProjects/cf-opencode/control-server.ts).

**Hot storage authority.** Stow’s existing Go `OpenWorkspace` uses one native directory/bucket over identical bytes: host file writes become S3 objects and S3 writes become real files. Its Runtime enforces API authority/accounting; direct host writes remain outside API quotas and are not sandboxed. Its advisory writer-session lock protects local liveness, not ownership across independently restored hosts. Close preserves data; destruction is explicit and refuses caller-adopted directories. [Actual implementation](https://github.com/chester-hill-solutions/stow-s3/blob/3bb3e890bbe56f11dd783c2ccfb9bd2813156919/pkg/stow/workspace.go) (blob `ee94cf1e48a82ff445275bd10a2340ca7711aab1`), [lock implementation](https://github.com/chester-hill-solutions/stow-s3/blob/3bb3e890bbe56f11dd783c2ccfb9bd2813156919/internal/storage/workspace/session.go) (blob `5ff9b22878ebe49207559e33e4df74985a010317`). No new POSIX shim is needed.

**Cold portability has two distinct forms.** Stow already exports/imports checkpoint archives, portable handoffs with digests, and adoption on another machine. Its contract requires paused writers; capture detects some concurrent change but supplies no live filesystem snapshot. Default exclusions include `.git`, `.stow` and sensitive-looking paths; integrity validation does not encrypt or scan content. Adoption creates a new workspace identity. These archives therefore cannot silently replace Aboiteau’s full session backups. [Pinned transfer contract](https://github.com/chester-hill-solutions/stow-s3/blob/3bb3e890bbe56f11dd783c2ccfb9bd2813156919/docs/contracts/task-manifest.md).

Aboiteau presently streams separate workspace/state tar archives, retains native metadata, uses SQLite `.backup` for OpenCode state, encrypts archives with framed AES-GCM, then publishes a manifest after uploading both parts. Its cold adapter needs streaming get/put, immediate head verification, size and `encrypted` metadata, paginated prefix lists and deletion. R2 credentials never enter Linux. Replacing the R2 binding with another object backend is a proposal; the current interface is R2-specific. Stow’s ordinary object-record backend and live Workspace backend are different surfaces; qualify required metadata rather than assuming universal S3 equivalence. [Archive implementation](/Users/ladmin/WebProjects/cf-opencode/src/conversation/checkpoints.ts), [wire contract](https://github.com/chester-hill-solutions/stow-s3/blob/3bb3e890bbe56f11dd783c2ccfb9bd2813156919/docs/contracts/compat-contract.md), [local metadata refusal patch](/Users/ladmin/WebProjects/cf-opencode/patches/stow/metadata-refusal.patch).

**Vault is portable ciphertext storage.** Vendored 0.2.0 exposes `VaultStore`, `SecretReader`/`SecretStore`, generic KV and memory adapters, HKDF workspace keys, AES-GCM, keyrings and explicit re-encryption. The host supplies authentication, authorization and master-key custody. Aboiteau currently supplies one environment master key and defaults workspace scope to `default`; namespace selection is not tenant authorization. KV updates/re-encryption lack compare-and-swap, and ciphertext does not authenticate the secret’s key name as AAD. Rotation needs serialized writes and an explicit archive-key migration strategy; archive encryption is separate from Vault’s versioned secret format. At-rest encryption also does not externalize inference credentials: existing onboarding/state-seed flows can populate OpenCode’s Linux state. [Vault core](/Users/ladmin/WebProjects/cf-opencode/vendor/chester-hill-solutions/vault/src/core.ts), [encryption](/Users/ladmin/WebProjects/cf-opencode/vendor/chester-hill-solutions/vault/src/encryption.ts), [host wiring](/Users/ladmin/WebProjects/cf-opencode/src/vault.ts), [readiness/credential sync](/Users/ladmin/WebProjects/cf-opencode/src/conversation/readiness.ts).

## Cloudflare boundaries and ownership hazards

Current touchpoints: `Conversation`/`Settings` Durable Objects and named RPC routing; DO transactional KV/SQLite, `agents/lifecycle` scheduling/alarms and `waitUntil`; native Container start/ports/exec/snapshots/interception; R2/`FixedLengthStream`; optional D1 tenancy, rate limits, Worker entrypoints and telemetry. Existing admission, runtime-access, checkpoint and Settings queues assume one owning actor. [Environment](/Users/ladmin/WebProjects/cf-opencode/src/env.ts), [scheduler](/Users/ladmin/WebProjects/cf-opencode/src/conversation/scheduler.ts), [Settings authority](/Users/ladmin/WebProjects/cf-opencode/src/settings-do.ts).

**Replacement requirements, not implemented capabilities:** retain transactional admission/idempotency, durable job epochs, cross-conversation spend/lease authority, single-owner fencing and restartable scheduling. Object uploads plus DB manifest publication remain a multi-step transaction; preserve orphan handling and old manifests until publication succeeds. Fence old hosts before restore, dispatch or deletion. Local Stow locks and process-local promises cannot establish distributed exclusivity. Cancellation acknowledgement does not prove descendant exit or settle unknown provider spend.

The existing authenticated control HTTP contract and pinned OpenCode server/client can remain: `/configure`, `/start`, proxy, split checkpoint/restore and readiness/accounting proofs. Rehost that Linux runtime and replace orchestration/storage/egress adapters; Stow provides workspace/storage primitives, not the durable conversation authority. This needs neither a new model loop nor treating Stow as a scheduler or security boundary.
